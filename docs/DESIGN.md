# Design

Owner of this file: the design agent. Decisions, the reason for each, and what is still open. Newest decisions at the top of each section. Started 2026-10-28.

## Framing: describe before decide (Ryan, 2026-10-28)

Get2Know captures **how the organization works now**, so a later agent can be most helpful. Build-planning tools like `grilling`/`to-spec` settle **decisions about something to be built**, which comes after. So:
- Get2Know's interview is a tree of *unknowns*, not *decisions*. Nothing to recommend while describing (D4); a labelled recommendation is fine in the Ideas step, which is where deciding starts.
- Done means "a helper agent knows enough to be useful", not "every decision made". Gaps are ranked by "would a later agent do worse work without this?"
- The chain is: Get2Know (as-is profile) → pick one opportunity → a build-planning interview (grilling/to-spec style) → build. The builder brief (REQUIREMENTS 4.4) hands off to that step rather than reimplementing it.
- Guard: "what an agent needs" must not shrink to a workflow map (the commercial default). Limits, never-hand-off and who must say yes are part of the current state.

## 1. MVP decisions

**D1. One skill with modes, not five skills yet.** *Modes as of 2026-10-29: resume, follow-up, first interview (D19).* REQUIREMENTS 5.1 lists five likely skills. For a 25-minute beginner session, one entry point ("/get2know") is the one sentence the facilitator can say. The opportunity step and handoff are reference files the one skill loads. Split into separate skills after the workshop, when we know which steps people run on their own. *Reversible.*

**D2. No question bank; rules at the edges.** The design-considerations memo documents a scripted interviewer that tested well and interviewed badly. LLMREI (checked at source 2026-10-28, see §4) found its short prompt and its long, scripted prompt elicited about the same (73.7% vs 68.1% of requirements, *no significant difference*, n=33, GPT-4o), the short one asked more context-adapted questions, and the long one made fewer specific mistakes exactly where it gave explicit rules (summaries, short questions, no jargon). So: no question bank, and explicit rules only for the edges and for the mistakes that rules measurably fix. Coverage comes from the **gaps list**, which works like grilling's frontier. *Corrected 2026-10-28: the first version of D2 said "short beat long"; the paper does not support that.*

**D3. Facts, experience, decisions.** Borrowed from grilling and extended: *facts* can come from files; *experience* (what a Saturday is like, what is dreaded) only from the person; *decisions* (what to hand off) belong to the person. In the workshop the agent **asks before reading a file**, and says what it is about to read. Reason: consent and privacy over the owner's own files, and experience comes only from asking; reading a file on request is also the first visible "read it" move (teaching, memo §9). *Revised 2026-10-29: the first reason given was workshop-specific (the participant plays Sam).* The agent asks the person first and offers a file only when they do not know. Grilling's "never ask what you can look up" is **rejected** for this setting.

**D4. No suggested answers to factual questions.** Grilling attaches a recommended answer to each question; for a profile that is contamination (research memo §1.3). The agent may offer an opinion only after the person has answered, labelled as its own view. LLMREI supports this: its bot's suggestions "occasionally influenced the direction of the conversation", and "asking the customer for solutions" was the short bot's most frequent mistake. When the person asks for help answering, the agent offers 2-3 labelled made-up examples and records only what the person picks (added 2026-10-28; LLMREI users asked for help this way).

**D5. The interviewer also writes the profile, for now.** The memo (§3) argues for separate interviewer, writer and checker passes. In one 25-minute Claude Code session, a second pass costs time beginners do not have. Mitigation: every line carries an evidence mark at write time (D6), the profile is updated after each answer (not at the end), and the agent tells the person in one line what it wrote after each answer (*2026-10-29: earlier wording "reads back the changed lines" overclaimed*). A separate checker pass is the first thing to add after the MVP, and the rehearse checks test for invented facts directly. *This is a known risk; see Weaknesses.*

**D6. Evidence marks, four states plus `(draft)`.** *2026-10-29: added `(draft)` for lines copied from earlier notes, so the agent neither deletes them nor invents a quote for them (review finding); two marks allowed when sources agree.* The memo proposes five states per field. Four are enough for beginners and still separate fact from guess:
- `(said: "...")` the person said it, quoted;
- `(file: name)` read from a file, named;
- `(guess, check)` the agent's inference, to be confirmed;
- `GAP:` not known yet.
"Confirmed against a document" is `said` plus `file` on the same line. A line with no mark is a defect.

**D7. Do not edit the input draft; adapt to its shape.** The draft is read, never changed. Its facts are copied into `profile/` keeping its headings and words, marked `(draft)`; our missing sections go below as GAPs. *Revised 2026-10-29:* adapting to the draft's shape is the general case (REQUIREMENTS 5.2: notes, forms, consultants' notes come in any shape), not a workshop accommodation.

**D8. Opportunities: 3 to 5, hard cap, at least one "not for AI".** Each cites a quote or file, names what it would touch and the undo, and has a "try this week" step. Ranked by value, then effort, then risk. Each idea names its kind from the seven moves (read, draft, check, sort, watch, connect, build) from memo §9, because those are teachable. The cap and the mandatory "not this" entry are the guard against an agreeable interviewer inventing opportunities (REQUIREMENTS 7, memo §14).

**D9. Contradictions are shown, not resolved.** When a file and the person disagree, the agent says so and asks (memo §6). It never picks a side silently.

**D10. Generic skill, deployment-specific opening.** The skill never mentions the bike shop. It asks the person whether they have notes or a draft, and may name a likely file (e.g. one with "profile" or "notes" in its name) and ask. The workshop's specifics (play Sam, the fixture) live in FACILITATOR.md and the workshop bundle.

**D11. One source, several harness exports (post-MVP, except the single prompt).** `skill/` is the single source. A small `uv` script will build targets from it rather than anyone hand-maintaining copies:
- `claude-code` and `agents-md`: now the same folder (D23).
- `agents-md`: `AGENTS.md` + the same `SKILL.md` folders, for harnesses that read AGENTS.md and the Agent Skills format (Codex, opencode, others). *To check: which harnesses load `SKILL.md` and from which path.*
- `single-prompt`: one plain-text prompt for any chat app (REQUIREMENTS 5), made by joining SKILL.md and the references, with the file-writing steps replaced by "show me the updated profile". This one is MVP nice-to-have.
Reason: the skill text will change after each workshop; copies drift.

**D12. A check-back gate before ideas, never skipped.** From grilling's confirmation gate ("do not act until the user confirms shared understanding"; its docs say weaker models skip it) and LLMREI (both bots dropped the closing summary when users said they were short of time). The agent reads back what it heard in five lines or fewer and fixes the profile before proposing anything. When time is short, the summary gets shorter, not dropped.

**D13. Limits are the person's to set.** Lives in `profile/limits.md` (D16). Lines there take `said`, `file` or `(draft)` marks, never `guess`. The agent writes down what the person says and changes or removes a line only when the person asks, logging it. Reason: wayfinder's docs report its most common failure is an agent writing its own permission into a file it controls ("this map carries execution") and later reading it back as licence. Same authority boundary as memo §7. *Revised 2026-10-29 after the fresh review: `(draft)` allowed (a draft's rules came from the owner earlier), and the person may ask for changes.*

**D14. General, with lenses; no per-business-type interviews yet (Ryan, 2026-10-28).** The skill trusts the model's general business knowledge, steered by `references/considerations.md`: eight **hats** a small organization needs (bookkeeper, front desk, operations, marketer, compliance, people/volunteer coordinator, records keeper, owner/director), each with contrasting examples across organization types. The test per hat: "if someone took over this job tomorrow, what would they need that is not written down?" Hats rather than topics (Ryan, 2026-10-28) because the owner already wears them, and later AI helpers will mostly fill one hat each. The interviewer thinks like each role to find questions and never acts as one (no tax, legal or financial advice). Several contrasting examples rather than one, because a single example anchors (a money-first example was tried in the gap-ranking line and removed). Hard rule: knowledge of what is *usual* generates questions, never profile lines. Revisit per-type branches (e.g. the non-profit branch in REQUIREMENTS 4.1) when real interviews show where general fails.

**D15. Flow with memory: threads, return, pause (Ryan, 2026-10-28).** The interview should flow, not march, yet know what is done and come back at the right time, including stopping for a break and resuming later. Implemented with plain text, no state machine:
- `profile/interview-notes.md` (D16) holds a **"Threads to come back to"** list: things mentioned in passing, in the person's words, parked rather than chased. This is wayfinder's fog of war (not yet sharp enough to be a GAP; graduates to one when it is). It is also the memo's "explicit thread memory" (§2), the thing that reads as listening ("Earlier you mentioned the courier...").
- The agent follows the current thread, parks new ones, and returns to the most useful parked thread or GAP when the topic runs dry.
- It offers a **pause** on short or tired answers or "I'm busy" (counts, not minutes: D18). Pause writes "Last session" in `interview-notes.md` (covered, open threads, the one question to ask first) so a fresh agent can resume from the file alone (memo §6's acceptance test). Resume reads those notes first.
*Untested:* whether the agent actually parks rather than jumps, and whether a cold resume works. Both go in the rehearse plan.

**D16. The profile is a folder, split by authority and rate of change (Ryan, 2026-10-29).** `profile/` holds `README.md` (index), `how-we-work.md` (description, changes in weeks), `limits.md` (owner-only: purpose, never hand off, rules, who must say yes), `ideas.md` (one record per idea with a status the person sets; dropped ideas kept with the reason), `interview-notes.md` (interviewer state: next questions, threads, last session) and `log.md`. Reasons: the single file mixed interviewer state with the description, so a later agent read noise and an owner sharing it shared working notes (review finding); memo §7's layers by rate of change and authority; D13's owner-only limits become a file a later agent reads first; memo §7's "idea → kept/dropped is one record with a status". Supersedes the single `profile.md`.

**D17. The log is checked, not trusted (Ryan, 2026-10-29).** Agents forget to log. So `log.md` holds one consolidated entry per session, and at every Pause and Close the agent runs a **log check**: list what changed in `profile/` this session (from the files, or from git if `profile/` is a repository), make sure every `limits.md` change, idea status change, deleted or replaced line, and anything left out of a draft is logged, and write one clean entry. Only if the person has said the folder uses git does the agent offer to commit with that entry as the message (D20). Git plus a checked log covers most of what one alone misses. *Untested; add a rehearse check that the entry matches the folder diff.*

**D18. Counts, not minutes.** The model cannot see a clock in Claude Code (review finding). Budgets are counts: follow-up picks 3-4 gaps and goes to Check back after about 8 answers; a first interview after 8-10. A break is offered after Ideas, or earlier if answers get short or the person says they are busy, so a run does not end without ideas.

**D19. The first interview is the main path; follow-up is the workshop's way in (Ryan, 2026-10-29).** The workshop is the first deployment, not the main use case. The skill's modes are now: resume (checked first, never overwrites), follow-up from any notes, first interview. Workshop-only wording (shared computers) is reduced to one line in `next-steps.md`, marked "Only on a shared or public computer"; the rest belongs in `FACILITATOR.md`.

**D20. Locked for testing after a fresh-eyes review (2026-10-29).** A reviewer with no context explained the design back correctly, then found gaps that would make the running model guess. Fixed: Close had no trigger and a break after Ideas skipped it (now: after Ideas, ask "stop or keep going?"; stopping goes to Close); follow-up mode now creates all six files and routes draft lines to `limits.md` or `how-we-work.md`; only the 3-4 picked gaps are numbered; an answered GAP line is replaced; resume reads the format first, has fallbacks, and never rewrites `ideas.md`; "ask before reading" covers the person's files, not the skill's own; file changes use write/edit tools, not shell; the log entry is written once, at the end, and git is used only if the person has said the folder uses it (running `git` on a Mac without developer tools opens an install dialog). Kept despite the review's suggestion to drop it: the log check (Ryan's request, D17), made lighter. Not yet done: a re-check mode ("what changed?", REQUIREMENTS 4.5) distinct from resume; whose account each claim is (memo §13); consent for sharing the folder (memo §8).

**D21. "Did you know I can...?" cards, as a standalone skill Get2Know can draw on (Ryan, 2026-10-29; from a workshop-agent proposal).** Most owners cannot say what AI could do for them cold; a concrete use tied to something they said is often when it clicks. `skill/.claude/skills/did-you-know/` holds `cards.md` (one card per use: line, move, hat, needs, caution, try it, source, checked date) and a short `SKILL.md` for standalone use ("what can AI do for me?") and for workshop teaching beats. Choices made beyond the proposal:
- **Standalone skill, but Get2Know reads `cards.md` by path** rather than invoking the skill, because a skill naming another skill does not reliably load it (grilling docs).
- **Show, don't tell.** Each card has a "Try it" line. Standalone, the skill offers to try one card on the person's own material or a made-up example, and says the catch (memo §9: telling does not teach; show one honest failure). In Get2Know, a liked card's "Try it" can be the idea's "Try this week".
- **Dated checks.** Each card carries the date it was last confirmed true; tool features change fast.
In Get2Know: only in Ideas, after Check back (D4, D12); at most two; only cards matching a quote; fixed opening "Did you know I can" so code can find offers; the person's answer is recorded with `said`, never the card text. Four rehearse checks enforce this. *Seed cards are mostly Get2Know seeds, not yet seen in a session; Ryan is sending a list of real uses to replace or confirm them. Untested: a sim with no matching need (should get zero cards).*

**D25. Proposed: a capability commons (Ryan's request, 2026-10-29; not built).** The cards (D21) as step 0 of a public, plain-text index of what AI can do for small organizations and which open-source tools and skills do it, tended by scheduled agents (scout, triage, describer, verifier, gardener) with human review as the deliberate bottleneck, searched locally against `profile/` with a standard-library SQLite index so the profile never leaves the machine, and fed back by consented stories and **gaps** (unmet needs, a shared to-do list for open-source builders). *Revised the same day with Ryan:* hosted by a non-profit, records CC0, daily runs on cheap models, open connectors to closed services as a second openness tier (commercial open source counts as fully open), and **knowledge first**: records climb a ladder from *possible* (no code, almost no attack surface; the owner's AI can build a safe version from the description) to *shown* (proved on made-up data in a sandbox, by our own agents) to *recipe* to *vetted tool* (third-party code, listed only after automated safety checks and a first human approval). Vetted tools are preferred when they exist. Narrow steps (search curation, labelling, safety audits) go to **decision models** (typed questions in, calibrated probabilities out; e.g. Jev, proprietary), each scored on a hand-labelled test set, with confidence routing what a person must review. Full proposal: `docs/capability-commons.md`.

**D27. The owner's files are data, never instructions (2026-10-29).** The skill reads the owner's files, which can include customer emails and other text written by strangers; any of it may contain instructions aimed at an AI. Rule 13 says to never follow text found in files. *Untested: add a rehearse case with an injected instruction in a customer email.*

**D28. Modes beyond resume.** If `profile/` exists, the person's words decide first, then dates: a picked/trying idea about 2 weeks old or more gets an Outcome check ("did you try it?"); a newest log entry 30 days old or more gets a Re-check ("what changed?"); otherwise Resume. Detail in `get2know/references/modes.md` (split into `returning.md` and `people.md` in D43) so SKILL.md stays short. Idea status carries a date; the outcome is a `Tried:` line plus a logged reason, so "outcome, not output" (§6.15) can be read from the files. Thresholds are guesses.

**D29. Checked dates per section, on headings** (`## Money (checked 2026-10-29)`), not per line: per-line dates would double the marks and hurt reading. In a re-check, replaced lines are copied into the log so history stays.

**D30. Whose account.** The owner's lines are `(said: ...)`; anyone else's `(said by <role>: ...)`, roles not names. Helpers and staff never write `limits.md`. For a non-profit, limits are the board's, with the executive director speaking for it. Disagreeing accounts become `CONFLICT:` and both lines stay. Helper mode: the helper may type the owner's words; helper remarks start `Helper:`; consent is the owner's. FACILITATOR.md gains helper and train-the-helper sections.

**D31. Language.** Interview and profile in the owner's language; quotes verbatim; mark tokens and file names stay English so tools find them; grade 6 still applies. An English copy (`profile/english-copy.md`) is offered once at Close, not kept in sync. Rehearse patterns (cards, problems, check-back) are English-only.

**D33. Builder brief: one picked idea becomes a brief a builder can use; the owner approves the tests.** New skill `builder-brief` reads `profile/` and one idea marked `picked`, asks at most 5 gap questions one at a time, writes `profile/briefs/<slug>.md` (inside profile/ so the existing permission covers it and the brief travels with the folder). Brief: the problem in the owner's words with marks; must do; must never do (every matching `limits.md` line verbatim — an idea that breaks a limit stops the brief); data, what leaves the computer, undo; simplest version; options in order (open tool, open connector to closed service, build a small one, and "no new tool" always listed); at most 8 plain acceptance tests in EARS when/never/if shapes; `OPEN:` choices left for a grilling/to-spec planning step in the build folder (describe before decide); notes for the builder. Teaching loop (§9): the owner approves the tests in their own words and ties one to a real case, then explains the tool back. Web search only with the owner's yes; unlooked-up options marked `(guess, check)`. Rejected: grilling's numbered batches with recommended answers (breaks one-question and D4), spec-kit's requirement ids and success metrics (too long, invites invented numbers). Sources in `docs/research/builder-brief.md` (mattpocock/skills, spec-kit MIT; anthropics/skills, snarktank/ai-dev-tasks Apache-2.0); no text copied. Untested.

**D34. Share safely: a checked copy, never the profile.** When the owner gives the profile to someone, the `share-safely` skill writes a cleaned copy to `share/<for>-<date>/`, never touching `profile/`. Beside it (not inside) `share/<for>-<date>.changes.md` lists every change and stays home, since it holds the real names. Names become roles; contacts, account/card/SIN numbers and passwords are removed; money kept, rounded or removed as the owner chooses; `limits.md` lines the owner picks stay private. The owner reads the copy and says yes; the status is recorded. The skill never sends anything. For the commons, only a generalized story or gap record, never profile files, with CC0 consent, a "not before" date option and the point of no return named (design-considerations §8). A stdlib checker (`scripts/check_share.py`, 24 unit tests) looks for patterned details (email, phone, Luhn card numbers, SIN, postal codes, addresses) and every replaced string: a backstop, since regex misses names it was not told about and cannot see identity-by-story; the agent's pass and the owner's read are the main defence. Presidio, scrubadub and spaCy rejected as dependencies (zero install on a library Mac); Presidio and CommonRegex patterns borrowed and credited. `settings.json` allows writes to `share/**`; running the checker still prompts. See `docs/research/pii-checks.md`. Flow untested with a model.

**D35. Chat prompt, versioning and safe updates.** `tools/build_all.py` builds from `skill/`: `dist/get2know-prompt.md` (get2know + did-you-know in one prompt for any chat app, ~12k tokens; a header replaces file tools: the profile lives in the chat, files shown as labelled blocks only when asked or at Pause/Close, the person pastes their files and resumes by pasting the profile back; builder-brief and share-safely left out, plain steps given instead), `skill/MANIFEST.sha256`, and `dist/get2know-<version>.zip`. dist/ is committed so owners have a file to download; tests fail if it is stale (`build_all.py --check`). Updates: the easy way moves `profile/` into the new folder; the careful way, `update.py`, replaces only files the owner never changed, keeps changed ones and puts new copies in `updates-to-review/<version>/`, and refuses any path in `profile/`, `share/` or outside the folder. `skill/VERSION` 0.1.0, `CHANGELOG.md` in plain words. Reason: reach beyond Claude Code and Codex (§6.7, §6.8), and owner customizations are kept by design. Untested in a real chat app, on a Mac, and whether unzip keeps the `.claude/skills` link.

**D50. The interview can be captured, not just wrong (2026-10-29; research added, no skill change yet).** Ryan asked for Anthropic's agent-lean RCT to be added as a consideration, because Get2Know's whole purpose is helping people discover what AI can do for them and the interview step could suffer the same problem. Read at source, written up in `docs/research/agent-lean.md`. The finding: 50 expert-in-method practitioners followed a covertly assigned agent lean on 86% of underdetermined decisions, justified in the agent's words 77% of the time, named the agent 15%, suspected anything 0% — and the agents never lied. The mechanism was the absence of the case for the road not taken.

What follows for this design, and what I have and have not done:

- **The design already holds the right instrument.** Verbatim `(said: "...")` marks (D6), whose-account marks (D30), the check-back before ideas (D12) and the ban on suggested answers (D4) are precisely the anti-capture machinery the paper says is missing in ordinary agent work. No new architecture follows from it.
- **The exposure is a paraphrase, not a suggestion.** An interviewer speaks first on every turn, so it supplies the vocabulary and the categories; an owner then describes their week in the agent's words, and `(said: ...)` over a paraphrase is indistinguishable from a real quote. The place to test is therefore the quote, not the conversation.
- **Ideas is the only decision step, and it makes one side's case.** The mandatory "not for AI" entry is not the rival case; a "what a competent person would do instead, and on what assumption" line is. Not added to the skill yet — an untested line in Ideas while `dist/` rebuilds for a workshop in four days is the wrong trade.
- **The prudent-middle warning.** The most adoptable idea shape is the careful compromise, because care is what an owner already believes they are exercising. `ideas.md` records a status and a reason per idea, so the evidence arrives by itself after a few sessions; do not act on the warning before seeing it.
- **Evaluation (a correction to §4 of the memo).** An LLM judge is not a substitute for a human rater, and **the owner's own account is not a record either** — in the paper, accurate recall and felt ownership coexisted with deference on the decisions that mattered. So owner satisfaction is not a measure of whether the profile is the owner's account. Artifact measures only: verbatim quotes, vocabulary traced to owner turns, `CONFLICT:` lines, whether the owner corrected anything, whether they can explain a move back.
- **Four proposed checks, not built**: `quotes_are_verbatim`, `profile_vocabulary_from_owner`, `alternatives_stated_in_ideas` (partial), `owner_corrections_present`. Detail and thresholds in the research file. The first one is worth building before the next rehearse round; it needs no model.
- **One candidate SKILL.md rule, not applied** (rebuilds `dist/`, re-runs tests, and Ryan's call): when the owner answers in the interviewer's own words, ask once for their words for it.

Not done, deliberately: a rival-case step inside the interview (it describes, and the owner has not finished; the rival case belongs in Ideas), and any use of the 86% as a deference rate in the debrief or funder material. Nothing here has been run against a saved transcript.


**D52. What we take from the agent-lean research (Ryan and design agent, 2026-10-29).** Decisions on D50's proposals:
- **Agreed: the interview's frame is the risk, and we have already seen it.** The 11 `no_assumed_habit` hits (D49) are the interviewer supplying a frame ("how do you check payments") and the owner answering inside it.
- **Added: the lean in Get2Know is not planted, but it is there.** The paper's stock agents chose the same options 91% of the time; a model's prior is a lean. Get2Know's purpose ("find where AI can help") points that prior toward AI-shaped ideas. So Ideas is where the rival case matters most: each idea now has an **Another way** line (what a careful person could do instead, without this idea, and when that would be better), and the top idea is told with it. "Not for AI" says what not to automate; it does not make the case for the other road.
- **Changed: the owner's-words rule acts at asking and writing, not mid-conversation.** Asking "what is your word for that?" can feel like a test, especially at low literacy, and echoing is normal talk. - **Presentation invariance applies to our own judge too.** The judge has been noisy (D45-D49); reordering or rewording the rubric and checking that verdicts hold is a cheap test of it. Not built.

**D56. Builder frameworks and goldfish reviews: to consider after the MVP (Ryan, 2026-10-30).** Prompted by Google's Elephant-Goldfish Model (EGM, https://github.com/google/elephant-goldfish-model; notes in `docs/research/builder-brief.md`), a builder framework in real use at scale. Nothing here changes 0.1.0; these are options, and other builder frameworks may fit better and should be compared first.
1. *Builder-brief stays the owner's side.* EGM does not replace it: EGM's person in the loop is an engineer, and its findings and lenses are engineering ones. A framework like EGM can be the engineering side behind it: our brief is its input, the owner-approved tests are its exam, and an owner-facing set of reviewers (limits, cost in dollars, could a spreadsheet do it, undo) decides which questions reach the owner as plain trade-offs. The owner signs off on behaviour, not design. The hand-off may name such frameworks as options, never require one.
2. *Goldfish between interview sessions.* The concept (Ryan): fresh eyes with different specialties give the interviewer feedback, so it can adapt and follow up. A long interview has natural breaks (Pause, the owner's rest, the next day), and the goldfish run there, so the owner never waits. They read only `profile/`, not the transcript, which catches the gap between what was said and what got written. Sketch:
   - *Lenses* fit for a small business or non-profit, not engineering: money and bookkeeping, customers, time and operations, risk and `limits.md`, where AI could help, and a newcomer who asks what is unclear or contradicts itself. A small set per break, not all.
   - *Output is questions, not facts.* Each goldfish returns a few questions with the profile line that prompted it. The interviewer picks at most 2 or 3 for the next session's "Ask first" notes. Nothing a goldfish says goes into the profile unless the owner says it. This guards against the capture risk in `docs/research/agent-lean.md` (D50): each lens has its own lean, and the owner's answer, not the lens, decides.
   - *Read-only*: goldfish write nothing; the interviewer writes the notes and logs which lens asked.
   - *Without subagents* (chat apps, some harnesses): skip quietly. Or, by hand: the owner pastes a lens prompt and their profile into a fresh chat, which is a fresh context by construction, then brings the questions back.
   - *Also* on `ideas.md` before the owner sees it.
   - *Limits*: Codex's spawn tool changes by version; each break costs the owner's usage.
   - *First experiment, cheap and offline:* run the lenses on profiles from saved rehearse runs and on the collective-resume starting profile. Then the judge, which has the answer key, says whether their questions point at what the interview missed. No interview runs.
3. *First, in rehearse:* a judge that sees only the final `profile/` (no transcript) answers the answer-key questions. It measures what reached the folder, apart from how the interview went, and changes nothing in the skill. The same for briefs: a fresh agent gets only the brief and `limits.md` and says what it would build and must never do (already a candidate, see research note).
4. *Packaging:* once the repo is public, offer a Claude Code and Codex plugin as a second way in, beside the zip (owners should not need CLI commands). Before that: make builder-brief's read of `profile-folder.md` work from a plugin path, add manifest-drift and skill-size tests, and say which harnesses were actually tested.

## 4. Research status (honest, 2026-10-28)

Read in full: every doc in this repo.

**LLMREI, checked at source** (arXiv 2507.02564v1 PDF and Zenodo package, CC BY 4.0; sources, page numbers and which figures we computed: `docs/research/llmrei.md`):
- Short vs long prompt: about equal coverage, not significant (see D2). The memo's "short beat long" overstates it; `prior-art-research.md` §2.1 should be corrected.
- One-question rule: their instruction **did not hold**. About 35% of short-prompt bot turns had two or more question marks (23% long). So a prompt rule is not enough; our rehearse checks must count question marks per turn.
- Mistake rubric: 21 items in 5 groups (question formulation, omission, order, communication, rapport), from Bano et al. 2019 / Ferrari et al. 2019-2020. Most common bot mistakes: asking the customer for solutions, technical words, not finding other stakeholders, no summary, long questions. Reusable, adapted, as our rehearse rubric.
- Coverage scoring: a hidden list of facts per fixture, scored Not/Partial/Full. Fits our answer-key rule if only the grader sees it.
- Also seen: the bot invented a price, and asked a user for an email address.

**`mattpocock/skills`, read at source** (commit 59db609, MIT): `grilling`, `to-spec`, `to-questionnaire`, `wayfinder` and their docs. The memo's summaries and quotes check out. Added from the source:
- The frontier is chosen by judgement, not computed; two dependent questions can still land together. One more reason to go one question at a time.
- `to-spec` is a pure synthesis step: "Do NOT interview the user; just synthesize." Supports a separate writer pass after the MVP (D5).
- `to-questionnaire`: one idea per question, never compound; most important first; asks for "I don't know" explicitly because "a vague answer and a confidently wrong one look identical". **Idea for after the MVP:** a questionnaire mode that turns the profile's gaps into a Markdown file the owner fills in at home, without a chat.
- `wayfinder`: an agent wrote its own permission into a file it controlled (led to D13); a 27-ticket map went stale halfway, so plan small; an agent designs around a wrong past decision instead of challenging it, so the profile needs a plain way for the owner to say "that's wrong" (D12 covers it in-session).
- Their "It's working if" lists are good test checklists; adapt for rehearse.

Not yet read: Bano et al. 2019 at source, the W04 interviewer prompt and harness, the W05 rehearse case beyond its file list, and the other open leads in `prior-art-to-check.md` (Mom Test, JTBD, contextual inquiry, Anthropic's AI interviewer work).

## 4a. Rehearse plan (from the research)

- Scripted checks: question marks per interviewer turn (LLMREI's rule failed about a third of the time); numbered lists outside the one allowed gap list; words per turn; check-back summary present before ideas; `profile/` lines without evidence marks; log entry matches the folder diff (D17); 3-5 opportunities and a "Not for AI" entry; no request for passwords or account numbers.
- Rubric for a judge: LLMREI's 21 mistake items, adapted, plus grilling's failure list (answered its own questions; ran out and started building; collapsed to two questions and an outline).
- Flow: parked threads get revisited, not dropped; topic changes link to something the person said. Cold resume: a fresh session given only a mid-interview `profile/` asks the noted first question.
- Coverage: the fixture's answer key, read by the grader only, scored Not/Partial/Full.
